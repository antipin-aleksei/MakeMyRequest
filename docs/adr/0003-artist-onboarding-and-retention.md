# ADR 0003 — Регистрация самостоятельных мастеров и хранение данных

Статус: Product decision captured, requires implementation
Дата: 2026-11-18

## Новые требования
1. Имя мастера, описание и контактная информация НЕ задаются разработчиком или через SQL seed: мастер регистрируется и заполняет их самостоятельно в onboarding-интерфейсе.
2. Для тестового сайта достаточно бесплатного HTTPS-адреса без собственного домена.
3. Заявки и прикреплённые референсы доступны мастеру до удаления из его кабинета.

## Последствия для архитектуры
- Исходная концепция «один заранее заданный мастер» меняется: система должна поддерживать регистрацию **нескольких независимых индивидуальных специалистов**, каждый получает собственную страницу/ссылку, но нет сущности «студия».
- Добавить аутентификацию и безопасную регистрацию мастера, `artist_accounts` / `artists` с уникальным `slug`, заполнение профиля и его публикацию.
- Публичный путь предпочтительно `/a/:slug` (или похожий адрес); заявки должны всегда связываться с конкретным `artist_id` из серверно-валидированной страницы.
- Настроить серверную проверку принадлежности заявок, референсов и статусов мастеру, **не** использовать один глобальный ADMIN_TOKEN для нескольких мастеров. Current MVP key must remain staging-only.
- Внести неизменяемые owner identifiers, индексы и тесты против cross-artist read/update, включая ссылки на объекты в хранилище.
- Реализовать soft delete/tombstone при необходимости пользовательского UX и физическое удаление заявки/референсов из PostgreSQL + object storage с учётом жизненного цикла резервных копий.
- «Хранить до удаления мастером» является продуктовым поведением, но не исключает применимые требования законодательства о защите данных: запросы на удаление со стороны клиента, установленные сроки, ограничения целей хранения и конфиденциальность.
- Бесплатные адреса провайдеров достаточны для теста. Render (Rust compute) и Neon (managed PostgreSQL) — предложенные поставщики, не обязательные зависимости архитектуры; выбор можно пересмотреть.

## Границы
Без студий и маркетплейса, без AI на этом этапе. Не публиковать MVP с одним общим ключом владельца как многопользовательский сервис.

## Следующий технический шаг
Прежде публичного тестирования создать отдельный roadmap/PR для регистрации, авторизации, профилей, tenant isolation и удаления заявок/объектов. Нынешние PR #1 и #8 не реализуют эти требования.
