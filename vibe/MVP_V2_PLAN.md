# План MVP v2 — аккаунты, запись по ссылке, локализация и анкета

Статус: **план, реализация не начата**. Дата: 2026-11-18.
Источник: требования владельца после проверки тестового сайта. Продукт — сервис независимых тату-мастеров и их клиентов; не студия и не маркетплейс.

## 0. Сначала устранить текущие поломки (P0)
- [ ] Выяснить, почему заявка, фактически отправленная в API, не видна мастеру: проверить БД Neon staging, artist_id, API и права доступа. Сверить ответ POST и запись в БД. Существующие заявки не удалять.
- [ ] Исправить прямое открытие и обновление `/admin` на статическом хостинге (SPA rewrite на `index.html` либо корректная серверная маршрутизация).
- [ ] Обеспечить доступ мастера к реально сохранённым заявкам через защищённый кабинет, а не через общий временный ключ.
- [ ] Smoke: отправка гостевой заявки → запись в Postgres → доступна только нужному мастеру → обновление страницы кабинета не даёт 404.

## 1. Зафиксировать маршруты и структуру экранов
- [ ] `/` — главная: логотип/краткое описание и **две точки входа**: «Я мастер» / «Я клиент»; регистрация и вход. Не показывать анкету записи на главной.
- [ ] `/auth/sign-in`, `/auth/sign-up` — вход/регистрация, роль мастера или клиента выбирается в onboarding (не доверять роли из браузера при авторизации).
- [ ] `/artist/onboarding` — настройка имени, bio, способов связи, профиля, публичной ссылки/slug.
- [ ] `/artist/dashboard` — заявки и профиль мастера; `/client/dashboard` — свои заявки и статусы.
- [ ] `/a/:slug` — публичный профиль мастера с кнопкой «Записаться/оставить заявку»; `/a/:slug/apply` — анкета только по уникальной ссылке мастера. Поддержать прямой переход/обновление URL.
- [ ] Не менять `/api/v1` без версии/обратной совместимости; при необходимости настроить redirect со старых URL.

## 2. Аккаунты и безопасная аутентификация
- [ ] Ввести сущность `users` с ролями/связями `artist_profiles` и `client_profiles`; предусмотреть один пользовательский аккаунт с возможностью быть и клиентом, и мастером, не смешивая права.
- [ ] Email + пароль как базовый способ регистрации/входа, безопасное хеширование паролей (Argon2id), подтверждение email, сброс пароля, сессии, logout и ограничение попыток входа.
- [ ] OAuth/OIDC: **Google, Apple, Facebook**; провести официальные callback flows через backend/Auth-provider, связывать социальные учётные записи только после проверки идентичности и не по совпадению непроверенного email. Кнопки показывать лишь для настроенных провайдеров.
- [ ] Для Apple и Facebook заранее нужны настройки разработчика и соответствующие credentials; до их подключения не обещать работающий вход. Не класть client secrets в `VITE_*`.
- [ ] Полностью убрать общий `ADMIN_TOKEN` как модель доступа к данным мастеров.
- [ ] Поддержать гостевую отправку заявки по публичной ссылке без обязательной регистрации; предлагать создать аккаунт позже. Привязка старых гостевых заявок только после безопасного подтверждения владения контактами.

## 3. Регистрация и профиль мастера
- [ ] При onboarding мастер заполняет отображаемое имя, описание, фото/аватар, город/условия, контакты и публичный `slug`.
- [ ] Автоматически выдавать персональный адрес вида `/a/my-tattoo-name`; кнопки «Скопировать ссылку» и «Скопировать ссылку на анкету».
- [ ] Мастер редактирует профиль, включает/выключает приём заявок и настраивает отображаемые способы связи.
- [ ] Публичная анкета принимает `artist_id` только через проверенный slug на сервере, не выбирает случайного первого мастера в БД.

## 4. Локализация RU / EN / SR
- [ ] Встроить i18n библиотеку с отдельными словарями `en`, `ru`, `sr`; локализовать публичную страницу, вход/регистрацию, кабинет, анкету, ошибки, статусы, уведомления и письма.
- [ ] Начальный язык: язык окружения браузера/WebView `navigator.languages` / системные настройки; `ru*` → русский, `sr*` → сербский, `en*` → английский, все остальные → **английский**.
- [ ] Ручной переключатель RU / EN / SR на главной и в кабинетах; сохранение предпочтения в аккаунте или локально для гостей. Ручной выбор имеет приоритет над автоопределением.
- [ ] Выбрать сербскую письменность на первом этапе: **sr-Latn** (латиница), архитектурно оставить путь к `sr-Cyrl`.
- [ ] Локализовать формат дат, чисел, валюты (без перевода вводимого пользователем описания тату автоматически).

## 5. Улучшенная анкета и контакты клиента
- [ ] Два поля габаритов татуировки: **ширина (см)** и **высота (см)**, оба числовые с разумными ограничениями; миграция/версия формы v2 и чтение старых ответов `size`.
- [ ] Место нанесения: понятные варианты + опция «Другое» и иконка `i` рядом с полем; по нажатию открыть адаптивное модальное окно с иллюстрацией человека, подписанными зонами (вид спереди/сзади). Иллюстрация оригинальная или с подтверждённой лицензией.
- [ ] Каналы связи: email, Telegram, WhatsApp, Viber, Instagram; можно указать несколько; **email не обязателен для заявки**, но обязателен для базовой email-регистрации, если не используется другая надёжная идентификация.
- [ ] Требовать хотя бы **один** способ связи; сохранять тип+значение, валидировать по типу (username/номер/адрес), защищать от XSS и не превращать пользовательский ввод в небезопасные ссылки.
- [ ] Для авторизованного клиента подставлять имя/контакты из профиля и **не заставлять повторно заполнять**; предусмотреть кнопку «Изменить контакт для этой заявки», если нужно.
- [ ] Для гостей показывать компактные контактные поля. Подтверждение отправки ≠ подтверждение записи на конкретное время.
- [ ] Серверный контракт и Postgres миграции под контактные каналы/габариты с обратной совместимостью и безопасным заполнением прежних записей.

## 6. Личный кабинет клиента
- [ ] `/client/dashboard`: список **своих** заявок с мастером, датой, статусом, подробностями и референсами в рамках согласованных прав.
- [ ] Профиль клиента: имя, доступные каналы связи, язык, привязанные OAuth-провайдеры.
- [ ] Просмотр деталей заявки; гостевые заявки автоматически не видны чужим аккаунтам. Опциональная привязка гостевой заявки после верификации владения контактом.
- [ ] В будущем подтвержденные бронирования — отдельная сущность; сейчас «Запрос на сеанс» означает только заявку.

## 7. Доработать кабинет мастера и разграничение доступа
- [ ] Список только **своих** заявок и фильтры по статусу; карточка анкеты, контактные способы, референсы.
- [ ] Кнопка перехода к Telegram/WhatsApp/Viber/Instagram/email в зависимости от указанного канала, без публикации контактов в открытом интернете.
- [ ] Изменение статуса заявки, редактирование/удаление своего профиля, удаление своих заявок и связанных изображений.
- [ ] Жёсткая проверка `artist_id` / `client_user_id` на сервере при чтении, обновлении, скачивании изображений и удалении.
- [ ] Удаление заявки по действию мастера: записи и связанные файлы из Postgres/private object storage; описать обработку ошибок удаления и резервных копий. «Хранить до удаления мастером» не отменяет возможные законные запросы клиента на удаление и требования GDPR.

## 8. Публикация и небольшая приёмка
- [ ] Миграции Neon **staging**, деплой Render API и frontend, маршруты SPA, CORS и HTTPS; использовать бесплатные адреса. Production-базу не трогать.
- [ ] Настроить OAuth redirect/callback URL для тестового домена; запретить публичное распространение до завершения auth и privacy-защиты.
- [ ] Небольшие фокусные тесты (не большой test-suite): (1) пользователь → заявка → кабинет клиента; (2) мастер → только свои заявки; (3) прямой `/admin`/dashboard URL не 404; (4) локаль; (5) загрузка/удаление приватного файла.
- [ ] Прогнать `npm typecheck/build`, `cargo fmt/clippy/test`, HTTP smoke на тестовой Postgres; проверить телефон, WebView и desktop.
- [ ] Устранить обнаруженные npm уязвимости, добавить базовый rate limiting/anti-spam, privacy/consent и доступный механизм удаления персональных данных.
- [ ] Сохранить итоги PR и список реальных блокеров: OAuth credentials, почтовый провайдер, приватное файловое хранилище, backups.

## Порядок реализации и принципы
**P0:** исправление видимости заявки и прямых URL → **P1:** данные пользователей, auth/role isolation, onboarding мастера и маршрутизация → **P2:** RU/EN/SR и анкета v2 → **P3:** кабинет клиента, контакты и удаление → **P4:** OAuth, тесты и staging.

Отдельные небольшие PR по этапам; не сливать в `main` без зелёных тестов. Использовать действующие `AGENTS.md`, skills и ADR, не переписывать код целиком без причины.

### Критерий готовности
Мастер регистрируется, настраивает профиль и делится персональной ссылкой. Гость либо авторизованный клиент по этой ссылке отправляет заявку с контактами и изображениями. Клиент видит свои заявки, мастер — только свои. RU/EN/SR работают, прямые ссылки открываются. Удаление мастером удаляет заявку и референсы. Социальный вход работает после подключения реальных OAuth приложений. Никаких автоматически подтверждённых сеансов.
